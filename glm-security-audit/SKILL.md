# GLM 安全审计流水线

来源:Trail of Bits `audit-context-building` + `code-maturity-assessor` 方法论,置信度门控参考 Sentry Security Review。**先建心智模型,再找漏洞。**

## 输入

目标仓库路径 + 范围约定(全量 / 指定目录)。无范围则默认全量。

## Phase 1 — 审计上下文(必做,禁止跳过)

1. 识别技术栈与框架(决定后续检查模式,不跑全语言通杀规则)
2. 通读入口文件,画出**一页数据流图**:外部输入 → 处理 → 存储/输出
3. 列出入口点表:每个入口标注**位置(file:line)+ 跨越的信任边界**
4. 确认"没有的东西":无 eval/exec?无密钥?无路径拼接?——负面发现同样写进报告

## Phase 2 — 威胁建模(STRIDE 快速通过)

对每条信任边界过一遍 STRIDE 六问,不适用的标 N/A 并一句话说明,不硬凑。

## Phase 3 — 发现(核心规则)

每条发现**必须**包含:

- **证据**:`file:line` + 代码片段,不接受"可能存在"
- **置信度**:高/中/低。**只详报高置信**;中低置信合并进"待观察"一节
- **攻击路径**:谁能利用、怎么利用、影响什么
- **变体分析**:发现一处,全库搜同类模式,报告所有变体位置

分类好的一面(负面发现):正确做了编码/无注入面等,给用户安全感。

## Phase 4 — 成熟度迷你评分(ToB 框架精选 5 维)

测试 / 文档 / 审计实践 / 算术安全 / 低级代码,各 0-5 分 + 一句理由。

## Phase 5 — 报告

固定结构:心智模型(含数据流图)→ 入口点表 → 发现(按严重度排序)→ STRIDE 表 → 评分卡 → 修复优先级(高中危在前,每条附具体修法)。

## 质量门

- 出报告前自检:每条发现有证据吗?高置信发现都复核过攻击路径吗?
- 修复建议必须可直接执行(给代码级修法,不给"加强安全意识")
