# AI-First 交付官

接到需求的第一反应不是写代码,是跑完这四步闭环:**穿透需求 → AI 协作交付 → 演示收反馈 → 沉淀复用**。

## 第一步:需求穿透(先问再造)

业务同学说"要一个 XX 工具"时,连问五个问题,把诉求翻到本质:

1. **不用这个会怎样?**(找到真正痛点,常发现他要的是另一个东西)
2. **谁、在什么场景、多久用一次?**(决定做成脚本、bot 还是平台)
3. **现在是怎么凑合的?**(竞品就是他的 Excel 和手工流程)
4. **怎么算成功?能举一个具体例子吗?**(逼出验收标准)
5. **最小版本明天能用,长什么样?**(砍出 MVP)

产出**一页纸方案**,四要素:背景(谁的什么痛)/ 目标(可验证)/ 验收标准(具体例子)/ 边界(这版不做什么)。拿这页纸跟需求方确认后再动手——返工成本从三天降到三分钟。

## 第二步:AI 协作交付

**起手式是和 AI 一起想,不是让 AI 直接写。** 先让 AI 复述它对方案的理解,列出它认为的风险和未知,再开写。

- 指令四要素:背景 + 任务 + 要求 + 格式
- 交付顺序固定:**跑通最小闭环 → 补错误处理与日志 → 补测试(至少覆盖主路径和边界)→ 部署**
- 按工具类型的检查清单:
  - **运营自动化工具**:人工干预点在哪?出错找谁?
  - **定时脚本**:失败重试?重复执行幂等?谁收到失败通知?
  - **对话 Agent / 飞书企微 bot**:答不上来时怎么兜底?敏感操作要不要人工确认?
  - **数据流水线**:脏数据去向?断点续跑?对账怎么验?
- 每完成一块,让 AI 自己 review 一遍再交付(判断力是人的,体力活是 AI 的)

## 第三步:演示与反馈(E 人打法)

向不熟的同事演示,用 30-30-30 结构:

- **30 秒痛点**:"你上周说每周一要手工导三张表,大概花两小时对吧?"
- **30 秒演示**:只演最核心的那一个动作,别演设置过程
- **30 秒价值**:"以后每周一 9 点自动发到你飞书,你只需要看。"

反馈必问三句:哪一步和你想的不一样?如果只能改一个地方,改哪?你旁边的同事谁还需要?

## 第四步:沉淀复用

**同一个问题第三次出现,就必须沉淀。** 判断标准:

| 情况 | 动作 |
|---|---|
| 只此一次 | 留 README 说明怎么跑 |
| 同类第二次 | 抽参数做成可配置脚本 |
| 第三次 | 沉淀为 skill / 内部工具,带上这次的教训 |

沉淀模板:`解决了什么问题(一句话)/ 怎么用(三条命令内)/ 踩过的坑 / 下次直接改哪里`。沉淀的目的不是归档,是让下一次交付从第 3 天变成第 3 小时。

## 质量门

- 没有一页纸方案不动手;没过需求方确认不开发
- 没跑通主路径不交付;没演示给使用方不算完成
- 交付后 48 小时内回收一次反馈
