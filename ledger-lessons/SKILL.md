# 台账蒸馏力：25 条 verified 事故 → 六类硬手法

> 来源：gaps.json verified 25 条（2026-09-27 ~ 10-24 累积），ZCode 于 10-24 按 Skill-DisCo 思路蒸馏。
> 每条手法后面括号标注出处编号，可 `mem-search query "<编号+关键词>"` 回溯原始 evidence。

## 一、口径纪律：报"全量"前的三道关

1. **数字不许硬编码**：结论行的"60/60 全绿"曾是字面量不是实算（T2）——报数必须来自当次实跑输出。
2. **范围必须声明**：机器上 7 家宿主，工具只看 5 家，"全宿主健康"就是假的（B2）——报"全量"必须附"看全了几家/漏了谁"。
3. **对账命令要可复现**：证据命令在 GBK 控制台直接崩（T1）——留证据前先在干净环境重跑一遍。

## 二、编码纪律：BOM 三连的血泪

4. **写文件一律 UTF-8 无 BOM**：4 个脚本带 BOM 直接语法错误跑不了（N7）；一个插件入口被写成 3 字节 BOM 空文件，DSH 启动中止（T8）。
5. **跨工具输出显式 utf-8**：输出编码跟随控制台代码页会导致跨工具花屏且当事工具看不出来（N9）——Python 读写/子进程一律 `encoding="utf-8", errors="replace"`。

## 三、工具可用性：能跑 ≠ 能交

6. **每个工具必须有 --help 且无参不执行本体**：8 个工具不认 --help，3 个无参即 Traceback（N8）。
7. **判据必须带回归用例**：R7/R8/R9 新判据上线时零用例，处于无保护状态（T4/C1）；修误报时先确认没把真检测一起修坏。
8. **新工具落位 + 登记**：主目录根和 Documents\Codex 的散落脚本违反落位规范（N1/N2）——工具进项目夹，登记进索引。

## 四、归因纪律：先分清"谁崩"再动手

9. **插件崩 ≠ 插件坏**：4 插件 8 工具全崩，真因是宿主返回结果过 post-execute 钩子时 `content.some` 崩（A1-A4）——先抓 OwningProcess/调用栈再定罪。
10. **修复动作本身要过验证**：单帧重压违反分帧约定，修复本身制造了新的会话不可读事故（T9）；格式版本约束（producer-owned）要先读懂再修（T7）。
11. **跨 RPC 边界的 None 防御**：openRemoteEvents 对 undef 崩（N19）——边界处一律 try/catch fail-open。

## 五、检索与语义层：诚实降级

12. **语义层不达标就降级，别硬上**：LightRAG 5 题闸门 1/5 未过 → 降级为"只回检索片段"，主力归 FTS（N13）。
13. **索引范围要覆盖台账与根文件**：gaps.json/根级 md 曾不在索引（N37，已修；SUGGESTIONS.jsonl 是尾巴）。
14. **作者标记要能过滤不只是显示**（N14，已修）——多 agent 同写一本记忆，检索必须按作者分流。

## 六、文件卫生：残留清理的门道

15. **保留名文件（nul）**：MSYS `rm` 可删，无需管理员（N6）。
16. **junction/链接迁移必须清宿主侧**：hot→pool 迁移不清 junction 就死链复发（B1）；`--audit` 抓不到"指错但目标存在"的链接（T3）——迁移一律走带清理的工具，不许手动 move。

## 出师自测（4 题，全对才许照此技能干活）

1. 要报"迁移后 60/60 全绿"，输出里必须出现什么？（实跑数字 + 宿主范围声明，不许硬编码）
2. Python 写一个会被 DSH 读的文件，编码怎么写？（UTF-8 无 BOM；读回来验证）
3. 8 个工具全崩，第一步做什么？（抓宿主调用栈定罪，别先动插件）
4. 语义层 5 题闸门只过 1 题怎么办？（降级为检索片段模式，主力归 FTS，诚实标注）
